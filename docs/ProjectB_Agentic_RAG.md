# 项目 B（新项目）：Agentic RAG 重构

> 定位：简历中的「最近实验」——证明会判断技术取舍，不只堆技术。
> 本质：**不是第二个项目，是 A 的第二次**。目标是"证伪 A + 重构 A + 量化收益"。

---

## 1. 一句话定义

用 PostgreSQL 一库到底替换掉 MySQL + Milvus + Redis；用本地 JEV 做 System 1 决策；LLM 只做 System 2 生成；新增**图片与图表的存储与检索**能力。

---

## 2. 四条升级

| # | 升级 | 预期收益（待实测） |
|---|---|---|
| U1 | PostgreSQL 一库到底（pgvector + JSONB + 全文 + trgm） | 运行时依赖 4 → 1；消除双写不一致；`pg_dump` 一份完整备份 |
| U2 | JEV（Qwen3.5-0.8B-JEV 本地）替代英文 BERT + LLM 策略路由 | 新增意图从"标注+重训"变为"改一行描述"；单次问答 LLM 调用 3 → 1 |
| U3 | Agent 工具路由 + 一次反思 | 尺寸/价格永不走文档检索；答不了主动转人工 |
| U4 | 图片 / 图表存储与检索（新 feature） | 打开"缺陷判定、安装示意"这类只有图能答的问题域 |

## 5. 实现流程

### T1｜PG 一库到底的 schema
- `pgvector`（HNSW）+ `JSONB`（chunk 元数据）+ `tsvector`（全文）+ `pg_trgm`（型号/标准号精确匹配）+ 业务表（含 `authority`、`experience` 相关表）
- 交付：`schema.sql` + 迁移脚本
- 验收：**关掉 Milvus 和 Redis 容器，系统仍能跑**

### T2｜语料与向量迁移
- A 的语料（含客服战地手册、历史工单、经验条目）迁入 B 的 schema；bge-m3 向量写入 pgvector
- 验收：同一批问题，A 与 B 的 top5 高度重合（迁移无损）；`pg_dump` 一份即完整备份

### T3｜JEV 部署与决策定义
- 加载 `Qwen3.5-0.8B-JEV`，HTTP 提供服务
- 四个判断：
  - `intent`：choice，7 类 + `other` 兜底
  - `need_structured`：noul，"此题必须查表"
  - `need_human`：noul，"必须转工程师"
  - `urgency`：score，3 档
- 验收：100 条领域问题实测准确率 + confidence 分布 + 单次决策耗时

### T4｜Agent 编排（工具路由 + 一次反思）
- 工具集：`search_docs` / `query_spec` / `query_price` / `search_experience` / `escalate` / `ask_clarify`
- 流程：JEV 决策 → 选工具 → 观察 → 判断是否够 → 生成或追问
- **边界：不做多 Agent 编排、不引入 LangGraph**（防过度设计）

### T5｜图片与图表（新 feature）
- `document_images`：`chunk_id / page_no / bbox / mime / caption / bytes`
- 起步 `bytea`（<200KB），预留 `object_key` 演进路径
- 图片经多模态模型生成 caption → caption 进向量库 → 命中后图文一并返回
- 验收：问"缺陷长什么样"能返回图 + 说明

### T6｜A vs B 对比评测
- 同一套 120 条测试集跑两遍
- 技术指标 + 业务指标（见 §3）
- 验收：一张对比表，每格实测

### T7｜前端升级
- 图片/图表卡片、置信度标识、路由路径可视化（演示用）

## 6. JEV 关键事实与约束

### 6.1 它是什么
- TypeSafe AI 的 System One Model 思想；老师给的是**本地开源实现**：Qwen3.5-0.8B 骨干 + 两层线性决策头（Wq / Wk）
- **不是云端 API**：离线、免费、客户数据不出内网（对工厂内网场景是优势）

### 6.2 原理
```
State:\n<上下文>\n Question (choice):\n<问题说明>\n Option:\n<候选1>\n ... Decision:\n
  → Qwen 骨干前向
  → 取 "Decision:" 末位隐藏态 → Wq → 查询向量 u
  → 取每个 "Option:" 末位隐藏态 → Wk → 候选键 v_i
  → z_i = u·v_i / sqrt(d) → softmax → 概率
```
**没有分类头，候选由文本描述决定** → 动态候选：加意图 = 加一行描述，不重训。

### 6.3 三种原语

| 类型 | 用途 | 返回 |
|---|---|---|
| `choice` | 分类 / 路由 | choice + 概率分布 + confidence |
| `score` | 分级打分 | score（期望值）+ level |
| `noul` | 是/否判断 | P(为真) + confidence |

### 6.4 必须遵守的约束

| # | 约束 | 原因 |
|---|---|---|
| C1 | `state` 只放"用户问题 + 少量历史"，**不塞检索文档** | `CUTOFF_LEN = 1024` 超限直接 raise，不截断 |
| C2 | 判断项 ≤ 4，或合并 | 每个问题一次独立前向 |
| C3 | 不改 `temperature` | 实现是直接除已 softmax 的概率且未重新归一化，≠1 时概率和 ≠ 1 |
| C4 | 设 `JEV_MODEL_DIR` 环境变量 | 权重路径写死为 Mac 绝对路径 |
| C5 | JEV 独立 venv / 进程 | A 用 torch 2.7.0 + transformers 5.10.2；JEV 要 2.7.1 + 5.5.3 |
| C6 | 用领域问题集实测；不准就改**候选描述文字** | 0.8B 对 Low-E / AS 1288 / IGU 等术语语感弱；改描述 = 改行为 |

### 6.5 confidence 三档路由

| confidence | 动作 |
|---|---|
| ≥ 0.85 | 自动执行 |
| 0.60 ~ 0.85 | 人工复核 |
| < 0.60 | 升级给 LLM / 人工 |

> 阈值必须用标注数据标定，不能拍脑袋。

## 7. 已确定的决策

| 编号 | 决策 | 理由 |
|---|---|---|
| E1 | PG 替代 MySQL + Milvus；Redis 也去掉 | 个位数 QPS，瓶颈在 LLM 而非 DB；组件 4 → 1。**不宣称"PG 比 Redis 快"**，而是"这个量级不需要 Redis" |
| E2 | 缓存降级为进程内 LRU（`cachetools`） | 单实例下比 Redis 快一个数量级，零运维 |
| E3 | JEV 独立进程 | 版本冲突 + 内存隔离 + 可独立重启 |
| E4 | Agent 只做"工具路由 + 一次反思" | 避免被判定过度设计 |
| E5 | 图片起步用 `bytea`，单独建表 | 单机小数据量；以后换 `object_key` 不动主体结构 |
| E6 | 第一版不上图数据库（GraphRAG） | 收益不确定、成本高；留作后续 |
| E7 | 嵌入与重排沿用 A 的模型 | 保证 A/B 对比只变架构、不变模型，归因干净 |
| E8 | 沿用 A 的"权威 / 经验"分级 | 这是业务规则，不因架构变化而变 |
| E9 | 经验沉淀闭环在 B 里升级为"可检索的经验库" | A 里是条目，B 里进入 Agent 工具集 `search_experience` |

## 8. 风险

| 风险 | 应对 |
|---|---|
| 0.8B 模型对玻璃术语判别不准 | 100 条领域测试集实测；调候选描述；不行则降级到 LLM 分类 |
| CPU 单次前向耗时偏高 | 减少判断项；合并判断；实测后再定 |
| JEV 高度依赖"候选描述质量" | 把描述当 prompt 工程对待，纳入版本管理 |
| Agent 编排易失控、难调试 | 工具数 ≤5；每条路径打日志；可视化路径 |
| 被判过度设计 | 边界写进文档；每条升级都要有实测收益 |
| 业务指标无法真实采集 | 用模拟日志 + 明确标注"估算口径"，不伪造 |
