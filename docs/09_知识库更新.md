## 1. 问题定义

知识库更新难，难点不在"替换文件"，而在**重建索引的同时保证语义一致**。

教学项目 `Itcast_qa_system` 的做法在此刻会直接崩坏，两个结构性缺陷：

### 缺陷 1：chunk id 用内容 md5

`vector_store.py` 中 `id = md5(page_content)`，随后 `upsert`。后果：

- 文档改一个字 → 新 id → **旧记录仍留在库里**
- 同一段内容的两个版本会被同时召回，召回质量随更新次数悄悄退化
- 没有任何字段能表达"这段是旧的"

### 缺陷 2：parent_id 用遍历序号

`parent_id = f"doc_{i}_parent_{j}"`，其中 `i` 是 `enumerate(documents)` 的**列表下标**。后果：

- 往目录里新增一份文档 → 后续所有文档的 `i` 变化 → **全库 parent_id 漂移**
- 父子关系整体错位，缓存全部失效，且无法察觉

### 结论

更新能力不是"加一个接口"，而是**先改数据模型**。本文定义该模型与流程。

---

## 2. 三条正确性要求

| 层级 | 含义 | 验收方式 |
|---|---|---|
| **结构一致** | chunk 数、父子关系、页号条款号与原文对得上 | 入库后做数量与抽样断言 |
| **语义一致** | 同一批问题，更新前后答案只在预期处变化 | 120 条测试集回归，指标不退化 |
| **可追溯** | 任一答案能回答"来自哪一版的哪份文档" | 响应中必须带 `doc_id` / `version` / `page` / `clause` |

第三层是本项目的**刚需**，不是加分项：不可能对客户说"我们的建议来自某一版标准，但具体哪版我不知道"。

## 3. 数据模型

### 3.1 三层职责划分（核心决策）

| 层 | 角色 | 存什么 | 不存什么 |
|---|---|---|---|
| **MySQL** | **事实源（source of truth）** | 文档元数据、全部 chunk 文本、状态、版本、经验条目、更新日志 | 向量 |
| **Milvus** | **派生索引（derived index）** | `id` + 向量 + 少量过滤字段 | **文本、状态** |
| **Redis** | 缓存 | 热问答结果（带 `kb_version` 前缀） | 任何权威数据 |

**为什么状态不放 Milvus：**

> 状态是**高频易变**的，向量是**昂贵**的。Milvus 更新一行非向量字段的语义是 `upsert`（delete + insert），
> 意味着改一个 `status` 就要重写整行（含向量）——这既低效又容易出错。
> 因此：**Milvus 只管召回，MySQL 管有效性。**

具体做法是**后置过滤**：Milvus 召回 top_k 个 `chunk_id` → 一次 `WHERE chunk_id IN (...) AND status='active'` → 丢弃失效版本 → 重新排序取 `final_k`。

代价与补偿：后置过滤会削减候选数，因此召回时**过采样** `top_k × 2`。

**关键收益：索引可重建。** 因为文本与元数据都在 MySQL，任何时刻都能从零重建 Milvus 索引，无需重新解析原始文件。这使得回滚成本极低（见 §6.3）。

### 3.2 MySQL：`documents`

```sql
CREATE TABLE documents (
  doc_id               VARCHAR(64)  NOT NULL COMMENT '稳定标识，不随内容/顺序变化',
  version              INT          NOT NULL COMMENT '文档版本号，从 1 递增',
  title                VARCHAR(255) NOT NULL,
  authority            ENUM('standard','manual','experience') NOT NULL,
  source_file          VARCHAR(512) NOT NULL COMMENT '原始文件相对路径',
  content_hash         CHAR(64)     NOT NULL COMMENT '整份文档 sha256，未变则跳过重建',
  chunking_config_hash CHAR(64)     NOT NULL COMMENT '切分参数指纹，变了必须全量重建',
  effective_from       DATE         NOT NULL,
  effective_to         DATE         NULL,
  status               ENUM('draft','active','superseded','archived') NOT NULL DEFAULT 'draft',
  chunk_count          INT          NOT NULL DEFAULT 0,
  ingested_at          DATETIME     NOT NULL,
  activated_at         DATETIME     NULL,
  PRIMARY KEY (doc_id, version),
  KEY idx_status (status),
  KEY idx_effective (effective_from, effective_to)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**约束**：同一 `doc_id` 下，`status='active'` 的行**最多一条**。由 `activate` 流程保证（见 §5）。

### 3.3 MySQL：`chunks`

```sql
CREATE TABLE chunks (
  chunk_id     VARCHAR(160) NOT NULL COMMENT '{doc_id}@{version}#{kind}{ordinal}',
  doc_id       VARCHAR(64)  NOT NULL,
  version      INT          NOT NULL,
  kind         ENUM('parent','child') NOT NULL,
  parent_id    VARCHAR(160) NULL COMMENT 'child 指向 parent；parent 为 NULL',
  ordinal      INT          NOT NULL COMMENT '文档内序号，稳定',
  text         MEDIUMTEXT   NOT NULL,
  content_hash CHAR(64)     NOT NULL,
  page_no      INT          NULL,
  clause       VARCHAR(64)  NULL COMMENT '如 AS1288-5.3.2',
  status       ENUM('draft','active','superseded','archived') NOT NULL DEFAULT 'draft',
  created_at   DATETIME     NOT NULL,
  PRIMARY KEY (chunk_id),
  KEY idx_doc_version (doc_id, version),
  KEY idx_status (status),
  KEY idx_parent (parent_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**命名规则（必须固定）**

```
parent_id = "{doc_id}@{version}#parent{k}"
chunk_id  = "{doc_id}@{version}#child{k}"
```

- `doc_id` 稳定 → 加文档不影响其他文档
- 带 `version` → 新旧版本可共存，不互相覆盖
- `ordinal` 在**同一 doc 的同一版本内**稳定 → 切分策略不变时，重建产生相同 id（幂等）

### 3.4 MySQL：`experience_entries`

经验条目**不走文件管线**，逐条 CRUD。

```sql
CREATE TABLE experience_entries (
  entry_id       BIGINT AUTO_INCREMENT PRIMARY KEY,
  question       TEXT     NOT NULL,
  answer_en      TEXT     NOT NULL,
  tags           JSON     NULL,
  status         ENUM('draft','active','archived') NOT NULL DEFAULT 'draft',
  confirmed_by   VARCHAR(64) NULL COMMENT '确认人（工程师/客服）',
  confirmed_at   DATETIME    NULL,
  effective_from DATE     NOT NULL,
  effective_to   DATE     NULL,
  source_ticket  VARCHAR(64) NULL,
  created_at     DATETIME NOT NULL,
  updated_at     DATETIME NOT NULL,
  KEY idx_status (status),
  KEY idx_effective (effective_from, effective_to)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

经验条目的检索走同一套向量索引，`doc_id` 取 `exp:{entry_id}`，`authority='experience'`。

### 3.5 MySQL：`ingest_runs`（留痕）

```sql
CREATE TABLE ingest_runs (
  run_id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  started_at        DATETIME NOT NULL,
  finished_at       DATETIME NULL,
  doc_id            VARCHAR(64) NOT NULL,
  version           INT NOT NULL,
  action            ENUM('add','update','archive','rebuild') NOT NULL,
  kb_version_before VARCHAR(32) NOT NULL,
  kb_version_after  VARCHAR(32) NULL,
  chunks_added      INT NOT NULL DEFAULT 0,
  chunks_deleted    INT NOT NULL DEFAULT 0,
  regression_passed TINYINT(1) NULL,
  status            ENUM('running','success','failed','rolled_back') NOT NULL,
  operator          VARCHAR(64) NOT NULL,
  note              TEXT NULL,
  KEY idx_doc (doc_id, version),
  KEY idx_started (started_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

用来回答："上周三那次更新改了什么、谁做的、有没有回滚。"

### 3.6 MySQL：`app_meta`（全局版本号）

```sql
CREATE TABLE app_meta (
  k VARCHAR(64) PRIMARY KEY,
  v VARCHAR(255) NOT NULL,
  updated_at DATETIME NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 关键行：kb_version 每次成功更新后 +1
INSERT INTO app_meta (k, v, updated_at) VALUES ('kb_version', '1', NOW());
```

### 3.7 Milvus collection `chunks`

只存**派生索引**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | VARCHAR(160) PK | 等于 MySQL `chunks.chunk_id` |
| `doc_id` | VARCHAR(64) | 过滤用 |
| `authority` | VARCHAR(16) | 过滤用（`standard`/`manual`/`experience`） |
| `page_no` | INT64 | 展示用 |
| `clause` | VARCHAR(64) | 展示用 |
| `dense_vector` | FLOAT_VECTOR(1024) | bge-m3 dense |
| `sparse_vector` | SPARSE_FLOAT_VECTOR | bge-m3 sparse |

**只索引 child chunk。** parent 不入向量库，检索命中 child 后按 `parent_id` 从 MySQL 取父块文本。

**没有 `status` 字段**——理由见 §3.1。

## 4. 四条更新路径

| 路径 | 对象 | 手段 | 时效 |
|---|---|---|---|
| **P1 表格类** | 能力矩阵 / 报价 / 交期 | **不进向量库**；MySQL `UPDATE` 或事务内整表替换 | 实时 |
| **P2 经验条目** | 战地手册 / 工程师口述 | 逐条 INSERT / UPDATE / 归档 | 实时（下一次检索生效） |
| **P3 文档类** | 设备手册 / 标准摘要 | 文档级全量重建 + 影子写入 + 回归门禁 | 分钟级 |
| **P4 切分策略变更** | 全部文档 | 全量重建（`chunking_config_hash` 变化触发） | 小时级 |

**P1 是最重要的一条**：价格、尺寸、交期这类"数字型知识"永远不进向量库，因此更新天然实时、天然一致，不存在索引问题。这条直接消灭了本项目一半的更新难题。

**为什么不做 chunk 级增量**：一份 25 页手册约 30–40 个父块 / 100–150 个子块，bge-m3 在 GPU 上重编码 150 条约 2 秒。为省这 2 秒去写 chunk diff 是过度设计；更关键的是——切分参数一改，**所有 chunk 边界变化、hash 全变**，增量逻辑直接失效。

## 5. 文档更新流程（P3）

### 5.1 状态机

```
draft ──activate──> active ──supersede──> superseded ──purge──> archived
  │                    │
  └──discard──> archived
```

| 状态 | 含义 | 会被检索到 |
|---|---|---|
| `draft` | 已解析、已切分，未生效 | ❌ |
| `active` | 当前生效版本（每个 `doc_id` 最多一条） | ✅ |
| `superseded` | 被新版本替代，等待清理 | ❌（但数据保留，可回滚） |
| `archived` | 作废，永久保留供追溯 | ❌ |

### 5.2 五步流程

**Step 1 `prepare`（不动线上）**

```
1. 读原始文件 → 解析 → 按来源切分（见 02_检索与生成规格）
2. 算 content_hash（整份）与 chunking_config_hash
3. 若 documents 已存在同 (doc_id, version)：
      status=draft  → 覆盖重写
      否则         → 拒绝（版本号不可复用，必须递增）
4. 写 documents(status=draft) 与 chunks(status=draft)
5. 输出 diff 报告：新增/变更/删除的 chunk 数、总字数变化、抽样对比
```

**Step 2 `verify`（结构一致）**

- chunk 数 > 0，无空文本
- 每个 child 都有对应 parent
- 页号 / 条款号非空比例达到阈值
- 与旧版本对比：chunk 数变化幅度超阈值（默认 ±50%）需 `--force`

**Step 3 `activate`（写入索引）**

```
1. 记录 kb_version_before，insert ingest_runs(status=running)
2. 从 MySQL 读 draft chunk → bge-m3 编码 → 写入 Milvus（新 id，不覆盖任何旧行）
3. MySQL 事务：
     UPDATE documents SET status='active',   activated_at=NOW() WHERE doc_id=? AND version=?
     UPDATE documents SET status='superseded'                    WHERE doc_id=? AND version<>? AND status='active'
     UPDATE chunks    SET status='active'                        WHERE doc_id=? AND version=?
     UPDATE chunks    SET status='superseded'                    WHERE doc_id=? AND version<>? AND status='active'
4. 提交事务（此时新版本已可被检索）
```

> ⚠️ 注意：此步**不删除 Milvus 里旧版本的向量**。旧向量仍能被召回，但后置过滤会因 `status='superseded'` 丢弃它。
> 这是**故意的**：保留旧向量 = 保留回滚能力。

**Step 4 `regress`（语义一致，门禁）**

- 跑 `08_评测方案` 的 120 条测试集
- 判据（任一不满足即失败）：

| 指标 | 允许变化 |
|---|---|
| Recall@5 | 下降 ≤ 3 个百分点 |
| 答案正确率 | 下降 ≤ 5 个百分点 |
| 幻觉率 | 上升 ≤ 2 个百分点 |

- 失败 → 自动执行 `rollback`（见 §6.3）

**Step 5 `commit`**

```
1. 删除 Milvus 中该 doc 所有 status != 'active' 的向量
2. MySQL：UPDATE ... SET status='archived' WHERE status='superseded'
3. kb_version += 1（app_meta）
4. Redis：旧前缀缓存自然失效（见 §7）
5. ingest_runs.status='success'，写入 kb_version_after
```

### 5.3 归档（文档作废）

```
1. UPDATE documents SET status='archived' WHERE doc_id=? AND version=?
2. DELETE 对应 Milvus 向量
3. kb_version += 1
4. ingest_runs(action='archive')
```

**不删 MySQL 数据**——追溯性要求答案能指向历史版本。

## 6. 一致性与回滚

### 6.1 为什么后置过滤是安全的

Milvus 只负责"候选集合"，MySQL 负责"是否有效"。即使 Milvus 里残留过期向量：

- 它会被召回
- 立刻被 `status='active'` 过滤掉
- 只浪费一点 top_k 预算（用 `top_k × 2` 过采样补偿）

**这是用"多一次 SQL 查询"换"不需要在 Milvus 里改状态"。** 对 130 条知识单元的规模，这笔交易极其划算。

### 6.2 失败点与后果

| 失败点 | 后果 | 恢复 |
|---|---|---|
| Step 3 编码中途失败 | Milvus 有部分新 id，MySQL 仍 draft | 删除新 version 的 Milvus 行，重跑 activate |
| Step 3 事务失败 | 同上 | 事务回滚，重跑 |
| Step 4 回归失败 | 新版本已 active | 自动 rollback |
| Step 5 删除失败 | 残留 superseded 向量 | 无影响（被过滤），下次重建时清理 |

### 6.3 回滚（因为索引可重建，所以便宜）

```
rollback(doc_id, version):
1. MySQL 事务：
     UPDATE documents SET status='archived' WHERE doc_id=? AND version=?        -- 新版本
     UPDATE documents SET status='active'   WHERE doc_id=? AND version<>? AND status='superseded'
2. DELETE Milvus 中 doc_id 且 version=new 的向量
3. kb_version += 1
4. ingest_runs.status='rolled_back'
```

如果旧版本的 Milvus 向量已被 commit 清掉，**从 MySQL 重建即可**（文本都在），不需要重新解析原始文件。

## 7. 缓存失效

Redis key 设计：

```
kb:{kb_version}:answer:{sha256(normalized_query)}
kb:{kb_version}:retrieval:{sha256(normalized_query)}
```

- 每次成功更新后 `kb_version += 1`
- 旧 key 不再被命中，按 TTL（默认 24h）自动回收
- **禁止使用 `FLUSHDB`**：无法区分"知识库更新"与"重启清缓存"，且 DB1 未来可能共享

`kb_version` 读取：启动时从 MySQL `app_meta` 读入进程内存；更新流程通过 Redis 发布一条 `kb:bump` 通知（可选，单实例可直接读库）。

## 8. CLI 规格

```bash
# 1. 准备（不动线上）
uv run python scripts/ingest.py prepare \
    --doc-id manual-tempering --version 2 \
    --file data/raw/manuals/tempering_rev_b.pdf \
    --authority manual --effective-from 2026-11-01
#   输出：diff 报告（新增/变更/删除 chunk 数、字数变化、3 条抽样）

# 2. 结构校验
uv run python scripts/ingest.py verify --doc-id manual-tempering --version 2

# 3. 生效（写索引 + 切换状态）
uv run python scripts/ingest.py activate --doc-id manual-tempering --version 2

# 4. 回归门禁（不达标自动回滚）
uv run python scripts/ingest.py regress --doc-id manual-tempering --version 2

# 5. 提交
uv run python scripts/ingest.py commit --doc-id manual-tempering --version 2

# 其他
uv run python scripts/ingest.py status                     # 列出所有文档与版本状态
uv run python scripts/ingest.py rollback --doc-id X --version 2
uv run python scripts/ingest.py rebuild --all              # 从 MySQL 全量重建索引
uv run python scripts/ingest.py archive --doc-id X --version 1
```

**统一要求**

| # | 要求 |
|---|---|
| C1 | 所有写操作默认 `--dry-run` 可预览，显式 `--yes` 才执行 |
| C2 | `prepare` 幂等：同 (doc_id, version) 重跑覆盖 draft，不影响 active |
| C3 | 每一步都写 `ingest_runs`，失败也写（`status='failed'` + note） |
| C4 | 任何一步失败，服务必须仍能正常回答（旧版本 active 不变） |
| C5 | 退出码：0 成功 / 1 失败 / 2 需要人工确认（如变化幅度超阈值） |

## 9. 明确不做的事

| # | 不做 | 理由 |
|---|---|---|
| N1 | chunk 级增量 diff | 切分参数一变即失效；规模不需要 |
| N2 | 自动监听文件目录变化 | 演示环境无此需求，且易误触发 |
| N3 | 多版本并存检索（同一 doc 同时返回两版） | 业务上只会造成混乱；只允许一版 active |
| N4 | 在 Milvus 里维护 status | 见 §3.1，易变字段不该进低效更新的存储 |
| N5 | 向量库直接存文本作为事实源 | 索引必须可重建，事实源只能有一个 |
| N6 | 更新期间停止服务 | 影子写入 + 后置过滤已保证一致性 |

## 10. M1.5 验收条件（DoD）

| # | 验收项 | 通过标准 |
|---|---|---|
| A1 | `prepare` 输出 diff 报告 | 能看到新增/变更/删除 chunk 数 |
| A2 | `prepare` 幂等 | 同参数跑两次，MySQL 中 chunk 数与内容一致 |
| A3 | `activate` 后新版本可检索 | 新问题命中新 chunk |
| A4 | 激活后旧版本不可检索 | 强制按旧条款措辞查询，不返回旧 chunk |
| A5 | `regress` 门禁生效 | 人为构造退化（如删除一个关键 chunk），流程自动回滚 |
| A6 | 回滚后服务正常 | 旧版本重新 active，答案恢复 |
| A7 | `kb_version` 递增且缓存失效 | 更新后旧 key 不再命中 |
| A8 | 加一份新文档不影响其他文档 | 其他文档 `chunk_id` 完全不变（验证缺陷 2 已修复） |
| A9 | `rebuild --all` 从 MySQL 重建索引 | 重建后 Recall@5 与重建前一致（±1pp） |
| A10 | `ingest_runs` 留痕完整 | 每次操作一行，含 kb_version 前后值 |
