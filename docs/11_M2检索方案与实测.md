# 11 · M2 检索：方案与实测

| 项 | 内容 |
|---|---|
| 里程碑 | M2 |
| token 消耗 | **0**（编码与重排都是本地模型） |
| 评测集 | `data/eval/eval_set.jsonl`，120 条，绑定 evidence chunk |
| 结果 | Recall@5 **88.1%**，MRR **0.779**，p50 **186 ms** / p95 **265 ms** |

---

## 1. 链路

```
问题文本
  → bge-m3 编码（dense 1024 + sparse 词权重）
  → Milvus hybrid 召回（dense 0.7 + sparse 0.3，带标量过滤）
  → 回 MySQL 取命中子块正文        ← Milvus 不存正文
  → bge-reranker-v2-m3 重排
  → 按父块去重（同一父块只留最高分）
  → 回 MySQL 取父块全文             ← small-to-big
  → 结果（正文 + 出处 + 分数）
```

## 2. 五个文件

| 文件 | 职责 |
|---|---|
| `retrieval/filters.py` | Milvus 标量过滤表达式（权威级 / 文档范围） |
| `retrieval/search.py` | hybrid 召回，返回 id 与出处，不含正文 |
| `retrieval/rerank.py` | CrossEncoder 封装，可与 embedder 分时驻留显存 |
| `retrieval/service.py` | 编排 + 父块还原 + 出处格式化 |
| `scripts/build_eval.py` / `eval_retrieval.py` | 出题与评测，均不调用大模型 |

## 4. 三个结论（按重要性）

### 4.1 权威分区对 Recall@5 没有影响（+0.0pp），只小幅改善 MRR（0.779 → 0.781）

我原本假设"问尺寸时不该让经验工单抢在前面"，做了按类别限定来源的对照实验。

结果是**没有提升**。原因看未命中明细就清楚了：正确答案本来就在 top-5 里，
过滤只能改变它排第几，改变不了它在不在。

**所以：权威分区不是提召回的手段，是控制"能不能对客户说"的手段。**
它的价值在 M3 的答案分级，不在 M2 的召回率。这条假设被数据否决了，记下来。

### 4.2 尺寸类 70% 是原理上限，不是调参问题 —— 这直接证明了 M4 的必要性

13 条未命中里有 9 条是同一模式：

```
Q: Can you make 4mm toughened glass 1950 wide by 2200 high?
期望: capability-matrix@1#child0   (toughened/flat/4)
实得: child7, child10, child13     ← 其他厚度/形状的行
```

能力矩阵的 30 行**结构完全一样，只有数字不同**：

```
Process=toughened | Shape=flat | Thickness (mm)=4  | Max width (mm)=2440 | ...
Process=toughened | Shape=flat | Thickness (mm)=5  | Max width (mm)=2440 | ...
Process=toughened | Shape=flat | Thickness (mm)=6  | Max width (mm)=2440 | ...
```

"4" 和 "5" 在语义空间里几乎重合，稠密向量**原理上无法区分**。
稀疏向量能捕捉到 `4` 这个 token，但在 0.7/0.3 的加权里权重不够。

**结论：这类问题不该用向量检索回答。** 正确做法是抽取 `thickness_mm=4`
然后 `SELECT ... WHERE thickness_mm = 4`——这就是 M4 的结构化槽位通道。

**这是本项目最值钱的一条发现**：不是"再调调参数就好了"，
而是"这类问题根本上不属于 RAG，属于查表"。

### 4.3 负面样例拒答率 0% —— 阈值机制不成立

11 条负面样例（超限尺寸、缺参数、语料外问题）全部没有被拒答。
当前用 `min_rerank_score = 0.35` 判定，但 reranker 的分数分布不支持这个阈值：
语料外的问题照样能拿到 0.4 以上。

**结论：拒答不能靠 reranker 分数，必须靠生成侧约束**（提示词 + 证据充分性判断），
属于 M3 的范围。当前阈值应视为无效，M3 要重新设计。

## 5. 踩到的坑

| # | 坑 | 处理 |
|---|---|---|
| 1 | **Milvus 静默丢数据** | 275 条向量里 `experience-fieldbook`(41) 与 `tickets-2025`(30) 消失，总数掉到 204，**不报错**。原因是入库后未逐份 flush。现在每份文档写完即 flush，并新增 `scripts/check_index.py` 做完整性校验（MySQL 每份文档的子块数必须等于 Milvus 里的向量数） |
| 2 | `load_collection` 偶发 `index not found` | 每次检索都 load 会在 Milvus 后台压缩期间撞上瞬时元数据不一致。改为只 load 一次 |
| 3 | fp16 与稀疏头 dtype 不匹配 | 模型 fp16、稀疏头 fp32，报 `mat1 and mat2 must have the same dtype`。稀疏头只有 1024 个参数，统一转 float32 即可 |
| 4 | 权威映射漏了一类 | `selection` 类里含 8 条经验题，第一版只允许 standard+manual，导致"权威过滤有害"的假结论。数据要看明细才能下判断 |

**坑 1 是最危险的一个**：向量库少数据不会报错，只会让某类问题悄悄检索不到。
如果没做分类别统计，这个 bug 会一直藏到演示当天。

## 6. 验收

| 项 | 标准 | 结果 |
|---|---|---|
| Recall@5 | ≥ 90% | ❌ **88.1%**（差 1.9pp，缺口全部在尺寸类） |
| MRR | 记录基线 | ✅ 0.779 |
| 延迟（不含生成） | < 1.5 s | ✅ p95 265 ms |
| 测试 | 全绿 | ✅ 117 passed |

**关于 Recall@5 未达标的判断**：缺口集中在 `spec`(70%) 与 `logistics`(70%)，
而这两类的失败原因是"该走结构化查询"，不是检索算法问题。
因此**不建议现在就为这 1.9pp 调检索参数**，应该在 M4 把尺寸类切到结构化通道后重测——
那时 `spec` 类会从评测集里分流出去，整体 Recall 自然会变。

这个决定要在 M4 之后复核，不能当作"已经解决"。
