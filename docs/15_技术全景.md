# 15 · 技术全景（面试与演示用）

> 这份文档回答一个问题：**这个项目里每一个技术选择、每一个参数，为什么是现在这个值。**
> 看完应该能应付"你们 top_k 设多少""为什么不用 BM25""索引怎么建的"这类追问。

---

## 0. 先说三件**绝对不能说错**的事

被问到时答错会直接掉分，因为面试官会顺着追问细节。

| ❌ 不要说 | ✅ 实际是 | 为什么危险 |
|---|---|---|
| "用了 BM25 做关键词召回" | 用的是 **bge-m3 的 sparse 向量**（模型学出来的词权重），存在 Milvus 稀疏倒排索引里 | BM25 有 `k1`、`b` 两个超参，面试官一问"你 k1 设多少"就露了 |
| "有 topM 参数" | **没有 topM**。HNSW 的构建参数是 `M=16`，检索时用 `ef=80` | Milvus 里 HNSW 没有 topM 这个名字 |
| "靠 rerank 分数低于 0.35 拒答" | 这个阈值**实测无效**，已弃用；拒答靠**模型自评**（输出 `INSUFFICIENT`） | 我实测过 11 条语料外问题，全部拿到 0.4 以上分数，阈值筛不掉 |

## 1. 端到端流程

```
【离线：建库】
  9 份原始资料（XLSX / DOCX / PDF / MD / JSONL）
        │  loaders.py —— 5 类 loader
        ▼
  统一 Block（文本 + 出处 + 页码 + 章节）
        │  chunker.py —— 按源类型选 5 种切分策略
        ▼
  父块 1200 字 / 子块 300 字（同一父块内切，重叠 50 字）
        │
        ├──► MySQL：documents / chunks（正文、状态、版本）  ← 事实源
        │
        └──► bge-m3 编码 → dense 1024 维 + sparse 词权重
                  │
                  ▼
             Milvus：chunks（只存 id、向量、过滤字段，**不存正文**）  ← 派生索引

【在线：问答】
  用户提问
     │  router.decide() —— 先抽参数
     ├─ 抽到厚度/宽高 → 查 MySQL 结构化表 → 模板渲染   ⚡ 1.2ms，0 token
     ├─ 抽到但不齐   → 追问（一次问全）
     ├─ 规格不存在   → 直接说清楚 + 给可选值
     └─ 什么都没抽到 → 向量检索
              │ bge-m3 编码问题
              │ Milvus hybrid_search（dense 0.7 + sparse 0.3，带标量过滤，limit=20）
              │ 回 MySQL 取命中子块正文
              │ bge-reranker-v2-m3 重排（20 条）
              │ 按父块去重 → 回 MySQL 取父块全文（small-to-big）
              │ 取 final_k=5
              ▼
         DeepSeek 生成（磁盘缓存）
              │ 首行标记 ANSWER / INSUFFICIENT
              │ 代码校验电话模式（≤3 句、每句 ≤60 字符、去 markdown）
              │ **代码拼出处**（模型不许写）
              ▼
         答案 + 出处 + 状态（answer / need_slot / refuse / escalate / service_error）
```

## 2. 技术栈

| 层 | 选型 | 版本 | 为什么是它 |
|---|---|---|---|
| 语言 | Python | 3.12.14 | 生态全；3.13/3.14 部分库还没轮子 |
| 包管理 | uv | 0.12.10 | 比 pip 快一个数量级，锁文件可复现 |
| Web 框架 | FastAPI | 0.115+ | 自带 OpenAPI；异步；和 Pydantic 一体 |
| ASGI | uvicorn | 0.30+ | FastAPI 标配 |
| 校验 | Pydantic | 2.8+ | 请求/响应模型即文档 |
| 事实库 | MySQL | 8.0.43 | 事务、版本、状态机天然合适 |
| 向量库 | Milvus | 2.4.15 (standalone) | 原生支持**稀疏+稠密混合检索**，这是选它的核心理由 |
| 缓存 | Redis | 7.2.16 | 规划中（M3 之后用于答案缓存），当前未启用 |
| 嵌入模型 | bge-m3 | 自实现加载 | 一个模型同时出 dense + sparse，省一套服务 |
| 重排模型 | bge-reranker-v2-m3 | CrossEncoder | 中文/英文/多语种都强，和 bge-m3 同源 |
| 推理 | PyTorch | 2.13.0+cu130 | GPU fp16，编码快 140 倍 |
| 变换器 | transformers | 4.57.6 | 直接加载，不用 FlagEmbedding |
| 重排封装 | sentence-transformers | 5.7.0 | CrossEncoder 三行搞定 |
| 大模型 | DeepSeek | deepseek-chat（实际回 deepseek-flash） | 便宜、中文好、OpenAI 兼容 |
| 日志 | loguru | 0.7.2 | 结构化、好用 |
| 前端 | 原生 HTML + CSS + JS | 单文件 | 没有构建步骤，改完刷新即见 |
| 桌面壳 | Edge `--app` + Win32 API | 零依赖 | 不用装 Electron/PySide6 |
| 测试 | pytest | 8.2+ | 210 条 |

**刻意没用的东西**（面试常问"为什么不用 X"）：

| 没用 | 原因 |
|---|---|
| LangChain / LlamaIndex | 会把检索细节藏起来。这个项目要能解释每一步，出问题要能定位 |
| FlagEmbedding | 它的 `BGEM3EmbeddingFunction` 会联网并长时间挂住（实测 >10 分钟无响应） |
| BM25 (rank_bm25/Elasticsearch) | bge-m3 的 sparse 已经覆盖词级匹配，且和 dense 来自同一个模型、同一个向量空间，融合更自然 |
| 现成 rerank 服务 | CPU/GPU 都要可控，自己封装 CrossEncoder 更透明 |
| Streamlit | 只能本地跑；FastAPI 同时给接口和页面 |

## 4. 关键参数（全部，带理由）

### 4.1 切分

| 参数 | 值 | 为什么 |
|---|---|---|
| `parent_chunk_size` | **1200 字符** | 生成的上下文要完整。手册一个章节通常 800–1500 字 |
| `child_chunk_size` | **300 字符** | 召回要精确。一整段 1200 字会稀释语义，300 字左右一句话一个点 |
| `chunk_overlap` | **50 字符** | 防止要点正好被切在边界上 |

典型比例：1 个父块 ≈ 4 个子块。**275 个子块 / 88 个父块 = 3.1**。

### 4.2 编码（bge-m3 自实现）

| 参数 | 值 | 为什么 |
|---|---|---|
| dense 维度 | **1024** | bge-m3 固定输出 |
| dense 取法 | **`[CLS]` + L2 归一化** | 归一化后内积 = 余弦相似度，Milvus 用 IP 就不用再算 |
| `max_length` | **1024 tokens** | bge-m3 支持 8192，但我们的块只有 300/1200 字，1024 足够且省显存 |
| `batch_size` | **16**（入库时可调到 8） | 8 GB 显存下 fp16 的稳妥值 |
| sparse 取法 | 稀疏头 → **ReLU** → 按 token 做 **max-pooling** | 同一个 token 多次出现取最大权重，符合词权重直觉 |
| 跳过的 token | `tokenizer.all_special_ids`，bge-m3 实际是 **[0, 1, 2, 3, 250001]** | 这些没有语义，留着会污染稀疏向量 |
| 精度 | **fp16（仅 CUDA）** | CPU 上 fp16 又慢又不准 |

实测：275 条子块，**GPU 约 1.3 秒，CPU 约 3 分钟（差 140 倍）**。

### 4.3 向量索引（Milvus）

| 参数 | 值 | 为什么 |
|---|---|---|
| 集合名 | `chunks` | |
| 主键 | `id` VARCHAR(160) | 形如 `manual-tempering@1#child12`，**按字节**限制长度 |
| 存储字段 | `id, doc_id, authority, page_no, clause, dense_vector, sparse_vector` | **不存正文**——正文只在 MySQL，避免两份数据不一致 |
| dense 索引 | **HNSW** | 不需要训练，小数据集（几百到几十万）上比 IVF_FLAT 更合适，召回更高 |
| `M` | **16** | 每个节点的邻接边数。16 是 HNSW 的常用默认值，召回/内存平衡 |
| `efConstruction` | **200** | 建索引时的搜索宽度。越大越准但越慢，200 是常用值 |
| dense 度量 | **IP**（内积） | 向量已 L2 归一化，IP 等价于余弦 |
| sparse 索引 | **SPARSE_INVERTED_INDEX** | 稀疏向量的倒排表 |
| sparse 度量 | **IP** | 与 dense 统一，方便加权融合 |
| 检索时 `ef` | **`max(64, top_k × 4)` = 80** | 检索宽度要大于 top_k；公式保证 top_k 变了自动跟着变 |

### 4.4 召回与重排

| 参数 | 值 | 为什么 |
|---|---|---|
| `top_k` | **20** | 每路（dense / sparse）各召回 20 条，融合后取 20 进重排 |
| 融合权重 | **dense 0.7 / sparse 0.3** | 语义为主、词面为辅。sanity：纯 dense 会漏型号/编号，纯 sparse 会被同义词坑 |
| 融合算法 | **WeightedRanker**（Milvus 内置） | 对两路分数加权求和，比 RRF 更可控（RRF 只看排名，丢掉了分数强度） |
| `rerank_candidates` | **20** | 送进重排的**硬上限**（`service.py` 里对候选切片）。实测重排耗时：4 条 184ms、8 条 344ms、12 条 628ms、**20 条 739ms**（约 37ms/条，CPU）。设成 20 = top_k，当前是 no-op，但它把"召回深度"和"重排深度"解耦了 |
| `final_k` | **5** | 进提示词的证据数。再多会稀释模型注意力，也更容易引入冲突信息 |
| `min_rerank_score` | **0.35（不参与决策）** | ⚠️ 实测 11 条语料外问题全部 >0.4，阈值筛不掉。**答案链路完全不读它**，只有评测脚本拿它判断负面样例是否被正确拒绝 |
| 重排模型 `max_length` | **512 tokens** | CrossEncoder 的常见上限，够覆盖 300 字子块 |
| 父块去重 | **按 parent_id** | 同一父块的多个子块命中时只留最高分那个，避免上下文重复 |

### 4.5 答案层

| 参数 | 值 | 为什么 |
|---|---|---|
| `phone_max_lines` | **3 句** | 客服在电话上照着念，超过 3 句客户会走神。由 `AnswerGenerator` 和 `templates.set_limits()` 从配置读取 |
| `phone_max_sentence_chars` | **60 字符** | 一口气能念完的长度。同上 |
| `low_confidence_threshold` | **0.6** | 低于此值标 `low_confidence`（当前用于标记，未做硬拦截） |
| `force_human_intents` | **`after_sales`** | 理赔涉及承诺，一律转人工 |
| 输出模式 | **按渠道分（phone / email）**，不按角色 | 同一个客服两种场景都要用 |

### 4.6 LLM

| 参数 | 值 | 为什么 |
|---|---|---|
| `provider` / `base_url` | deepseek / `https://api.deepseek.com` | OpenAI 兼容，换供应商只改配置 |
| `model` | `deepseek-chat` | ⚠️ 该账号实际返回 **deepseek-flash**，所以日志额外记录响应体的 `model` 字段 |
| `temperature` | **0.1** | 要稳定、可复现。答案内容是抄资料，不需要创造性 |
| `max_tokens` | **1024** | 电话模式 3 句、邮件模式一小段，1024 绰绰有余 |
| `timeout_s` | **60** | |
| `max_retries` | **2** | 直接传给 openai SDK，用它的指数退避重试（自己写容易漏掉 429 和 5xx 的区别） |
| 缓存键 | `sha256(model + temperature + max_tokens + system + prompt)` | 任何一项变了就重算，避免拿到旧结果而不自知 |
| 缓存位置 | `outputs/llm_cache/{hash}.json` | 调试提示词时重复跑同一批题**不重复花钱** |

### 4.7 数据与表

**7 张表**，分两类：

| 类别 | 表 | 说明 |
|---|---|---|
| 检索类 | `documents` | 文档清单，主键 `(doc_id, version)`，状态机 |
| | `chunks` | 子块/父块正文，`kind` 区分，`status` 控制可见性 |
| | `ingest_runs` | 每次入库的审计记录 |
| | `app_meta` | 全局 KV（`kb_version` 等） |
| 结构化类 | `capability` | 能力矩阵 30 行：工艺 × 形状 × 厚度 → 最大宽/高/面积/公差 |
| | `pricing` | 报价 20 行：含 GST 单价、最低收费、MOQ、**成本价（永不返回）** |
| | `leadtime` | 交期 10 行：工艺 × 厚度上限 × 数量上限 → 工作日 |

**为什么分两类**：`chunks` 里那几份表格的文本副本用于**模糊兜底检索**；
三张结构化表用于**精确匹配**。职责不同，不是重复。

### 4.8 chunk 标识与状态机

```
manual-tempering@1#parent3     父块
manual-tempering@1#child12     子块
        ↑          ↑  ↑
      doc_id    version 序号
```
**版本是标识的一部分**——同一文档的 v1 和 v2 是两套独立的块。

```
draft ──► active ──► superseded ──► archived
           │
           └── 检索只看 active
```

### 4.9 权威分级

| 级别 | 来源 | 说话方式 |
|---|---|---|
| `standard` | 澳洲标准摘要 | 可以直接说"必须" |
| `manual` | 厂商手册 | 可以直接说 |
| `experience` | 工单、老师傅经验 | **必须说成 Usually / In our experience**，不能当规范 |

实现上：只要证据里出现 `experience` 来源，代码就强制加对冲前缀（不依赖模型自觉）。

### 4.10 配置项与代码的对应关系

> 面试时如果说"这个参数控制 X"，面试官可能追问"代码在哪一行"。
> 所以这张表如实标注每个参数**到底有没有被读取**。

| 配置项 | 是否生效 | 读取位置 |
|---|---|---|
| `parent_chunk_size` / `child_chunk_size` / `chunk_overlap` | ✅ | `ingest/chunker.py` |
| `top_k` / `dense_weight` / `sparse_weight` | ✅ | `retrieval/search.py` |
| `rerank_candidates` | ✅ | `retrieval/service.py`（候选切片） |
| `final_k` | ✅ | `retrieval/service.py` |
| `phone_max_lines` / `phone_max_sentence_chars` | ✅ | `answer/generator.py` + `answer/templates.py` |
| `temperature` / `max_tokens` / `timeout_s` / `max_retries` | ✅ | `answer/llm.py` |
| `min_rerank_score` | ⚠️ 只在评测 | `scripts/eval_retrieval.py`（答案链路不读） |
| `low_confidence_threshold` | ❌ 预留 | 当前没有统一的置信度标量，`low_confidence` 由"格式违规 / 含经验来源"等规则触发 |
| `force_human_intents` | ❌ 预留 | 需要先有意图分类（M4c），当前售后类靠生成侧自然判断 |

**这是刻意公开的**：两个"预留"参数对应的是还没做的功能（意图分类器），
留着是为了让配置表达完整设计意图，不是为了假装已实现。
如果面试聊到，主动说"这两个我声明了但没接入，因为对应能力在 M4c，而槽位路由已经够用"——
比被问出来强得多。

## 6. 八个关键设计决策（面试重点）

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | MySQL 是事实源，Milvus 只是派生索引 | 改状态不用动向量库；向量库丢了能重建 |
| 2 | 出处由代码拼，模型不许写 | 模型会编页码，而且编得很像真的 |
| 3 | 尺寸价格类走查表，不走向量 | "4" 和 "5" 在语义空间几乎重合，**原理上分不开** |
| 4 | 路由判据是"有没有抽到参数"，不是意图分类 | 省掉一个 BERT 分类器和 800 条标注数据 |
| 5 | 拒答靠模型自评（`INSUFFICIENT`），不靠分数阈值 | 阈值实测筛不掉语料外问题 |
| 6 | 父子块（small-to-big） | 小块好召回，大块好生成 |
| 7 | 经验来源强制加对冲前缀 | 合规要求：经验不能冒充标准 |
| 8 | 唯一编排入口 `flow.run()` | 避免"评测跑的路线和线上不一致"（踩过，negative 只有 45%） |

## 8. 面试速答

### 30 秒

> "玻璃厂客服是英文母语、工程师是中国人做不了英文电话，设备文档又全是英文。
> 每来一个技术问题就要打电话问工程师再自己翻译，一个电话十几分钟。
> 我做了个英文知识助手：客服输入问题，30 秒内拿到能直接说的英文答案并带出处。
> 尺寸价格类走查表，1.2 毫秒、不花 token；模糊问题才用大模型。
> 检索 p95 247 毫秒，答案状态正确率 98%。"

### 被问"参数怎么定的"

> "top_k 20、重排 20、最终 5。重排那条我实测过：4 条 184ms、8 条 344ms、
> 12 条 628ms、20 条 739ms，大约 37 毫秒一条。20 条是延迟和收益的平衡点，
> 再多延迟就压不住 p95 了。HNSW 用 M=16、efConstruction=200，
> 检索时 ef 取 max(64, top_k×4)=80，这样 top_k 改了 ef 自动跟着变。"

### 被问"为什么用 bge-m3 的 sparse 而不是 BM25"

> "bge-m3 一个模型同时出稠密和稀疏，稀疏那路是模型学出来的词权重，
> 不是 BM25 的 TF-IDF。好处是两路来自同一个模型、同一个语义空间，加权融合更自然；
> 坏处是不像 BM25 那样有明确的可解释性（k1、b 这些）。
> 我选它主要是为了少维护一套索引服务。"

### 被问"召回率 88.7%，剩下 11.3% 呢"

> "全部集中在尺寸类和交期类。原因是这两类问题的表格行**只有数字不同**，
> '4mm' 和 '5mm' 在语义空间几乎重合，稠密向量原理上分不开。
> 所以我加了结构化通道——这两类在线上走查表，实测 100%，根本不进检索。
> 检索里保留它们是为了持续记录这个上限。"

### 被问"拒答怎么做"

> "早期想用重排分数卡阈值，实测无效：11 条语料外问题（潜艇玻璃、熔点、营业时间）
> 全部拿到 0.4 以上。后来改成让模型首行输出 ANSWER 或 INSUFFICIENT，
> 代码只认前缀；认不出就按资料不足处理，转人工。
> 原则是宁可转人工，不可瞎答。"
