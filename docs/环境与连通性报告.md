### 7.1 执行中发现的坑（已修）

**坑 1：模型目录校验误报。**
最初 `ModelsConfig.missing()` 只判断 `is_dir()`。而 ModelScope 下载时会
**先建目录、写 config.json，权重却是 0 字节的 `.incomplete`**，
于是 `check_env` 报"模型目录 OK"，实际模型不可用——错误会被推迟到真正加载模型时才炸。

修法：改为要求 `config.json` + **非空**权重（`model.safetensors` / `pytorch_model.bin`），
并支持分片索引（`*.safetensors.index.json`）。已补对应单测，覆盖"有目录无权重""0 字节权重""分片索引"三种情况。

**坑 2：ModelScope `modelscope download` CLI 卡死。**
它创建了 4 个 `.incomplete` 占位文件后长时间零进展（flax/rust/tf 权重也一并排队）。

改用文件直链逐个下载，只取 transformers 需要的 5 个文件：

```
https://modelscope.cn/api/v1/models/AI-ModelScope/distilbert-base-uncased/repo?Revision=master&FilePath=<file>
```

**坑 3：`pkg_resources` 被新版 setuptools 移除。**
pymilvus 2.4.x 在 import 时就 `from pkg_resources import ...`，而 setuptools ≥80 已删除该模块。
已在 `pyproject.toml` 固定 `setuptools<80`；同步后锁定为 79.0.1。

### 8.1 执行中发现的坑（都已处理）

**坑 1：CUDA 版 torch 下不动（已解决）。**
RTX 5060 Ti 是 Blackwell(sm_120)，必须用 CUDA 12.8+ 轮子。但实测：

- `download.pytorch.org`：连接建立后**不传数据**，10 分钟零进展
- `mirrors.aliyun.com/pytorch-wheels`：0.54 MB/s，3.4 GB 需 **约 105 分钟**
- 清华 / 北外 / 南大 镜像：无 `cu128` 路径（404）

**先用了 CPU 版跑通流程**（275 条编码约 3 分钟，可接受）。

**最终解法**：机器上原本就有一个 conda 环境 `bert_gpu`，里面是
**torch 2.13.0+cu130**，且其 Python 3.12.13 与本项目 3.12.14 同一小版本，二进制兼容。
实测该 torch 的 `arch_list` 含 **sm_120**，能认出 5060 Ti 并正常执行 kernel。

把 `torch` / `torchgen` / `functorch` / `dist-info` 从 conda 复制进 `.venv` 即可，
已固化为脚本 `scripts/use_conda_torch.ps1`（含 CUDA 可用性与 sm_120 检查、失败退出）。

**实测加速**：64 条 chunk 编码 —— CPU 约 1.5 条/秒，CUDA 约 **209 条/秒**（≈140 倍）；
275 条从 3 分钟降到 1.3 秒。

⚠️ `uv sync --extra ml` 会重新装回 PyPI 的 CPU 版 torch，**每次 sync 后要重跑该脚本**。

**顺带修掉的一个 dtype bug**：CUDA 上模型以 fp16 运行，而稀疏头权重是 fp32，
直接相乘报 `mat1 and mat2 must have the same dtype`。改为在池化前把隐藏态统一转 fp32
（顺带也让 normalize 与 relu 更稳）。

**坑 2：`milvus_model` 的 BGEM3EmbeddingFunction 加载会挂住。**
它内部依赖 `FlagEmbedding`，加载时访问 HuggingFace 且**不报错、不超时**，
实测挂起 10 分钟以上。而 `transformers` 直接加载本地权重只要 **0.8 秒**。

**处理**：自己实现编码（`retrieval/embedder.py`）——
dense 取 `[CLS]` 隐藏态 + L2 归一化；sparse 用 `sparse_linear.pt` 头过 relu 后按 token id 做 max 池化。
已从依赖里移除 `milvus-model`。验证：`12mm toughened glass 2400 3000` 的稀疏权重
最高项正好是 `glass / 12 / tough / 2400 / 3000 / mm`。

**坑 3：`HF_HUB_OFFLINE` 必须显式设置。**
不设时 transformers 会尝试联网补齐可选文件。已在编码器里 `os.environ.setdefault` 强制离线。

**坑 4：Milvus 的 VARCHAR `max_length` 按字节算，不按字符算。**
`clause` 字段按字符截到 64，加上省略号 `…`（3 字节）后变成 66 字节，写库报
`the length (66) of 0th VarChar clause exceeds max length (64)`。

**处理**：新增 `clip_utf8()` 按字节截断，`chunker` 与写库路径统一使用。

**坑 5：Milvus 的 `row_count` 不可信。**
`get_collection_stats()["row_count"]` 把**已删除**的行也算进去：重复索引 30 条后
它从 275 变成 305，而 `query(count(*))` 仍是 275。

**处理**：`MilvusStore.count()` 改用 `query(..., output_fields=["count(*)"])`。

**坑 6：`uv run` 在依赖变动后会重新同步，可能长时间无响应。**
开发期间改用 `.venv\Scripts\python.exe` 直接调用，命令行写在 README。
