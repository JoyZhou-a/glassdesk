# 10 · 代码导读（不用看代码也能懂）

> 这份文档写给三种读者：半年后的你、面试官、以及接手的人。
> 目标：读完能说清"这个系统怎么运转的"，不需要读 Python。

---

## 1. 一句话

**把一堆格式各异的英文资料（PDF / Word / Excel / Markdown / 工单），
变成数据库中一条条"能被人查、能被引用、能追踪出处"的知识碎片。**

后面 M2 要做的"检索"、M3 要做的"回答"，全部建立在这些碎片之上。

---

## 2. 数据是怎么流动的

拿一份设备手册举例，走一遍：

```
① data/raw/manuals/tempering.docx          ← 原始文件（Word）
        │
        │  解析：把 Word 拆成一块块结构
        ▼
② Block 列表（101 块）
        │  段落 32 条 / 标题 10 个 / 警告 8 条 / 表格行 51 行
        │
        │  切分：按章节打包成"父块"，再把父块拆成"子块"
        ▼
③ Chunk 列表（14 个父块 + 79 个子块）
        │  每个 chunk 自带编号、出处、内容指纹
        │
        │  落库
        ▼
④ MySQL 两张表
     documents  一行 = 一份文档的一个版本  →  记录标题、权威级别、状态
     chunks     一行 = 一条知识碎片        →  记录正文、出处、属于哪个父块
```

**为什么要分两步（Block → Chunk）？**
因为"解析"和"切分"是两个独立的问题。解析关心"Word 里有什么结构"，
切分关心"切多大合适"。混在一起的话，将来改切分参数就得动解析代码。

## 4. 五个必须懂的概念

### 4.1 `doc_id`：文档的身份证

```
manual-tempering    ← 钢化炉手册
capability-matrix   ← 能力矩阵
std-summary         ← 标准摘要
```

**它不是文件名。** 文件名改了、内容改了，`doc_id` 不变。
所以"这份手册的第 1 版和第 2 版"能被认成同一份文档，版本号才能串起来。

登记在 `data/seeds/docs_manifest.yaml`，查不到就报错，不让程序猜。

### 4.2 `chunk`：一块知识碎片

```
chunk_id = manual-tempering@1#child12
           └─ 哪份文档 ─┘ │  └ 第几个子块
                        版本
```

里面带三样东西：
- **正文**（`text`）：真正被检索的内容
- **出处**（`page_no` / `clause`）：第几页、哪张表、哪条标准
- **指纹**（`content_hash`）：判断这块内容有没有变

### 4.3 父块与子块：为什么要两层

| | 子块 | 父块 |
|---|---|---|
| 大小 | 约 300 字，小 | 约 1200 字，一整节 |
| 作用 | **用来被搜到**（小而准） | **用来给模型读**（大而全） |
| 数量 | 275 | 88 |

流程是：**用子块去搜 → 搜到了就把它所在的父块整段交给模型**。

好处：搜索时精准，回答时上下文完整。这叫"small-to-big"。

### 4.4 权威级别：这条知识能不能对客户说

| 级别 | 来源 | 能不能照直说 |
|---|---|---|
| `standard` | 澳洲标准 | 能，但必须带条款号 |
| `manual` | 设备手册、能力矩阵、报价表 | 能，必须带出处 |
| `experience` | 客服经验、历史工单 | 只能说"通常 / 我们一般" |

**这是合规要求，不是技术偏好。** 把经验当标准说，出事就是赔钱。

### 4.5 状态：一条知识现在算不算数

```
draft → active → superseded → archived
草稿    生效中    被新版替代      已作废
```

检索时**永远只看 `active`**。旧版本不删，留着供追溯（"去年我们建议的是这个"）。

## 5. 三个"为什么这样设计"

这三条都是教学项目的坑，也是面试时最能体现工程判断的地方。

### 5.1 为什么表格要拆成"一行一块"，还带列名

教学项目把 Word 表格**逐单元格拍平成一行字符串**，二维关系全丢。
结果："12mm 对应的最大宽度是多少"这种问题根本答不出来。

我们的做法是每行存成：

```
Table 2-1 Furnace specifications — Parameter=Nominal max panel width | Value=2440 | Unit=mm
```

**一行脱离表格也能读懂。** 这是整个项目中对检索质量影响最大的一处设计。

### 5.2 为什么 chunk 编号不按"第几个文件"来

教学项目用 `parent_id = doc_{i}_parent_{j}`，`i` 是**遍历文件时的序号**。
往目录里加一份新文档，后面所有文档的 `i` 都变 → 全库编号错位、缓存全部失效。

我们改用 `doc_id`（稳定的身份证）打头，加文件不影响任何其他文档。

### 5.3 为什么版本不能随便覆盖

如果允许直接覆盖正在生效的版本，会出现这个局面：

```
documents 表说：这份文档是 active（生效中）
chunks    表说：它的碎片还是 draft（草稿）
```

**检索侧会一条都搜不到。** 系统表面正常，实际静默失能——这种 bug 最难查。

所以代码里加了一道保护：已生效的版本不能被静默重写，必须升版本号
（`--version 2`）或显式 `--force`。

## 7. 面试怎么讲这一段

> "入库这块我做了三件事。第一，把 PDF/Word/Excel/Markdown/工单五种格式统一成
> 一个中间结构，解析和切分分离，改切分参数不用动解析代码。
>
> 第二，表格不拍平——每一行单独成块，并且前置列名和表标题，保证这一行脱离
> 表格也能被理解。这是检索质量的关键，也是很多教学项目的死穴。
>
> 第三，chunk 的身份按 `文档ID@版本#序号` 设计，而不是按遍历序号。这样加一份
> 新文档不会让全库编号漂移，而且新旧版本能共存、能回滚。"

**如果被追问"你怎么保证不静默失能"**：

> "我加了一层状态一致性保护。我发现如果允许覆盖正在生效的版本，会出现
> documents 是 active 但 chunks 是 draft 的状态，检索侧一条都搜不到，
> 而且不报错。所以我让 prepare 在遇到已生效版本时直接拒绝，必须升版本号。"
