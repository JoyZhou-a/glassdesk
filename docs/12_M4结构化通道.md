# 12 · M4 结构化槽位通道：方案与实测

| 项 | 内容 |
|---|---|
| 里程碑 | M4a + M4b（M4c 意图分类器押后） |
| token 消耗 | **0**（全链路不导入 openai，评测时可证） |
| 结果 | 结构化类 60 题 **100%**，负面样例外 11 条全部安全处理 |
| 依赖 | M1b 的 chunks（文档兜底）+ 新增三张结构化表 |

---

## 1. 为什么要有这条路

M2 的实测：尺寸类问题 Recall@5 只有 **70%**。看未命中明细发现原因不是算法：

```
Q: Can you make 4mm toughened glass 1950 wide by 2200 high?
期望: capability-matrix@1#child0   (thickness=4)
实得: thickness=5 / 6 / 8 的行
```

能力矩阵 30 行**结构完全一样、只有数字不同**。"4" 和 "5" 在语义空间里几乎重合，
稠密向量原理上分不开——**这不是调参能解决的问题**。

结论：这类问题不该用 RAG，应该抽参数查表。这就是结构化通道存在的理由。

---

## 2. 链路

```
问题文本
  → slots.extract()        正则抽厚度/宽高/数量/工艺/形状/涂膜/规格串
  → slots.validate()       三态：complete / missing / no_slots / bad_value
  → structured.StructuredLookup
       capability  → 判定能不能做（宽、高、面积、最小尺寸四个判据）
       pricing     → 单价（成本价永不返回）
       leadtime    → 工作日数
  → templates              电话模式（≤3 行/句≤60 字）或邮件模式（结构化）
```

**全程不调用大模型。** 数字只能来自表——这是 PRD 的红线，尺寸价格答错是赔钱事故。

## 3. 路由判据：不看意图，只看参数

原设计想先训一个 BERT 意图分类器。现在不需要了：

> **判据是"有没有抽到可计算的尺寸参数"，不是"这是什么意图"。**

- 抽到 `thickness=12, width=2400, height=3000` → 必然要查能力矩阵
- 什么都没抽到（"Why does IGU fog up?"）→ 走文档检索
- 只抽到一部分（"Can you make a big one?"）→ 追问，不猜

这条判据贯穿 M4，也让 M4c（分类器）从必需变成可选。

## 6. 踩到的坑

### 坑 1：四舍五入把夹胶规格算错

`_to_mm()` 最初保留 1 位小数，把 **6.38 变成 6.4、8.76 变成 8.8**，
于是夹胶的 10 条题全部校验失败（报"没有 6.4mm 这个规格"）。

夹胶的公称厚度是 6.38 / 8.76 / 10.76 / 12.76，**必须保留 2 位**。
这类错误只看代码很难发现，是拿 60 条真题跑一遍立刻暴露的。

### 坑 2：评测集本身有缺陷——同一题目、不同答案

第一次跑 93.3%，4 条失败全在 config。查下去发现是**出题的问题**：

报价表里同一厚度的平板和异形、无膜和有膜是不同的行（8mm 平板 145、异形 310），
而出题时题面只写了厚度和工艺，于是生成了多个**文字完全相同、答案却不同**的题目，
系统无从区分。

修法：题面必须包含 shape / variant / coating。改完后 100%。

**教训：评不出来先怀疑评测集，不要急着改系统。** 如果当时去调系统参数，
就会为了迁就一个坏题目把正确的逻辑改坏。

### 坑 3：报价查询没按规格串过滤

`6-12-6` 和 `6-16-6` 价格不同，但查询只按 (工艺, 形状, 厚度) 匹配，
随机命中一个。修法：抽出规格串后作为 SQL 条件，客户没说才退回按涂膜/无膜排序。

---

## 7. 口径说明（重要）

M4 之后，评测集被分成两组，**指标必须分开报**：

| 组 | 题目 | 走哪条路 | 指标 |
|---|---|---|---|
| 结构化类 | spec 30 / config 20 / logistics 10 | 查表 + 模板 | 答案数值正确率 **100%** |
| 检索类 | after_sales 32 / selection 17 | 向量检索 | Recall@5 **100%** |
| 兜底 | negative 11 | 追问 / 拒答 | 安全处理率 **100%** |

**把两类混成一个总分是不诚实的**——它们的失败模式完全不同，一个是数字算错，
一个是没检索到。混在一起会掩盖问题。

另外：结构化类的 ground truth 是从同一份 CSV 派生的，所以严格说是"自证"，
它验证的是**抽取 + 查表 + 渲染这条链路的正确性**，不是独立验证数据本身。这一点必须说清楚。
